# C04 revision trajectories and checkpoint cohorts

Introduced in 0.1.0.dev4; supported in 0.1.0. See [INSTALL.md](INSTALL.md) for
current installation qualification. Example paths also work after exporting
with `structdet-code examples --output ./examples`. Production commands inspect
passive records and never execute candidates or infer missing agent actions.

## Start with a supplied study

```bash
python3 -m structdet_code trace --study examples/minimal/study.json --format markdown
python3 -m structdet_code trace-template --study examples/trace/study.json --output /tmp/structdet-trace-template.json
python3 -m structdet_code trace --study examples/trace/study.json --design examples/trace/concentration.json --format markdown
```

`trace` without a design reports the available per-run histories. Its generated
design leaves checkpoints, budgets, stopping ordinals and protocol unknown, so it
does not create a cohort trend automatically. `trace-template` saves this same
starter design to a new file. Existing outputs are refused.

The study already contains exact source artifacts, assignments, receipts, runs,
revisions and feedback. Its version remains `structdet-code.study/0.2`.
Preparation from a plain source directory still creates standalone snapshots;
it cannot invent an earlier agent history. Import actual parent IDs, revision
ordinals and feedback/receipt bindings into the study before claiming a history.
The shipped study is a complete example of the portable record format. Provider-
specific log importers are outside C04.

## Trace design fields

| Field | Meaning |
| --- | --- |
| `schema_version` | `structdet-code.trace/0.1` |
| `trace_id` | Bounded ASCII identifier |
| `study_sha256` | Exact study manifest bytes |
| `configuration_id` | One existing study configuration ID, or null while unknown |
| `protocol_ref` | Supplied common recording/collection protocol, or null |
| `clock` | `revision_ordinal` |
| `selection_rule` | `declared-path-exact-ordinal/0.1` |
| `checkpoints` | At most 32 strictly increasing actual integer ordinals, each 0..1000000; empty for trajectories only |
| `runs` | At most 128 explicit roster entries |
| `assessments` | One record for every recorded revision in the roster, including excluded branches; at most 512 |

The roster chooses the study scope explicitly. Other study runs are listed as
outside the roster. When several configurations are present, the template leaves
the configuration null; select one, keep its desired runs, and keep exactly their
revision assessments. All recorded roster runs must belong to the chosen
configuration before a checkpoint cohort can be analyzed. Unknown configuration
leaves per-run trajectories available and cohort aggregation unavailable.

A run entry has this shape:

```json
{
  "run_id": "C1",
  "missing": false,
  "path": ["C1-V0", "C1-V1", "C1-V2"],
  "stop_ordinal": 2,
  "budget": {"max_revision_ordinal": 2, "max_test_case_attempts": 60}
}
```

`missing: true` explicitly represents a planned run absent from the study. Its
ID must not already exist in the study, and both path and stop ordinal must be
null. Its budget may be known from the plan. A misspelled absent run with
`missing: false` is an input error, with no automatic promotion to a missing run.

An assessment has the same three selection fields used by static inspection:

```json
{"revision_id": "C1-V0", "assignment_id": "M-fifo_good", "receipt_id": "E-C1-V0"}
```

Null assignment and receipt IDs mean unadmitted or unassessed evidence. Otherwise
the assignment must be the latest recorded version for the exact artifact and
the receipt must belong to that exact revision. Even an identical-byte final
artifact does not let its receipt certify an earlier revision. Conflicting hard
labels for identical source bytes in one trace fail with
`trace_conflicting_classes_for_same_source`; preserve a review disagreement as
an unresolved/conflicted assignment before measuring it.

The template uses the latest assignment already in the study. It preserves an
explicit study receipt selection when present. At other revisions it selects a
receipt only when exactly one exists. With several receipts, the choice remains
null, regardless of which result passed. Choose the intended evaluation receipt
explicitly; all other receipts remain visible as additional test evidence.

## Branches, missing steps and stopping

`path` chooses one recorded lineage. It lists revision IDs in their actual order,
following direct parents. It starts at a recorded root or missing-ancestry
boundary and ends at the study's selected endpoint when that endpoint is known.
Known intermediate parents cannot be omitted, and sibling branches cannot be
joined merely because their ordinals are consecutive. A merge requires an
explicit incoming-parent choice. Other parents and all excluded revisions remain
in the report. There is no branch-population estimator in C04.

The template can follow an unambiguous chain backward from an explicitly selected
endpoint, or recognize a fully recorded unique linear chain. It leaves ambiguous
merge choices null. A null path retains all per-run records but selects no
checkpoint observation for that run.

A supplied path can bridge a missing direct parent, with the continuation
retained as unresolved lineage. That bridge contributes no supported adjacent
transition. A direct parent edge from ordinal 0 to ordinal 3 retains the gap and
its endpoint labels; it is not recoded as three observed revisions or one ordinary
adjacent switch. At checkpoints 1 and 2 the revision is missing.

Stopping time is separate from endpoint selection. A run can select an earlier
branch after inspecting a later one. Supply a `stop_ordinal` only when the actual
stopping position is known. It requires a study stop reason of `success`,
`failure`, `budget` or `timeout`, and cannot precede any recorded revision. With
unknown stop time, the report preserves the terminal reason without guessing
when the run left the cohort.

At every checkpoint, the cells distinguish observed, stopped by each terminal
reason, excluded branch, missing revision, unknown path, unknown stop time,
not recorded at that checkpoint and explicitly unrecorded run. No endpoint is
carried forward. Risk sets show known stopped-before, known reached and unknown
reach separately. The `not_known_stopped` list includes unknown reach; it is not
a claim that those runs executed the requested step.

## Evidence, budgets and supported transitions

Budget can be null, or an object whose two values can independently be null.
`max_revision_ordinal` is an upper ordinal bound from 0..1000000, not a count of
model calls. `max_test_case_attempts` is a supplied run-wide bound from
0..1000000000. Actual model-call budgets and wall-clock durations are outside
this carrier. The protocol reference should identify what revision ordinals mean,
how branches/endpoints were selected, how stopping works, and what tests were
shown to the agent.

Usage reports count recorded revisions, generation roots, no-ops, receipts and
attempted/completed test cases. Test totals sum all supplied receipts of the run,
including repeated tests and excluded branches. They describe recorded claims;
unrecorded work is unknown. Exceeding a declared limit is preserved as an excess,
and prevents a qualified numeric contrast. Requested checkpoints outside the
declared revision limit also prevent a qualified contrast.

The per-run sequence keeps every source identity, label/state, selected validity,
test observation, incoming parent, missing parent, received feedback and endpoint.
Feedback receipt identity, agent visibility and ancestry use the original study
checks. A withheld test cannot become agent-visible feedback. Receipts attached
to the same revision have no independent event clock; their within-revision
chronological order is unspecified.

| Selected-path edge state | Treatment |
| --- | --- |
| `mechanism_switch` | Admitted labels differ on a consecutive-ordinal, single-parent edge with changed bytes |
| `source_change_same_mechanism` | Changed bytes, same admitted label on that supported edge |
| `unchanged_source_and_mechanism` | Same bytes and same admitted label on that supported edge |
| `unresolved_assignment` | At least one endpoint lacks an admitted label; no switch count |
| `ordinal_gap` | Actual ordinals skip positions; keep endpoint information, exclude from adjacent transition counts |
| `missing_lineage` | Supplied continuation across missing ancestry; no supported switch |
| `merge_parent_comparison` | Selected incoming parent compared with the merge output; separate from ordinary transitions |

Supported class-to-class counts include the first three states, including
same-class transitions. Their observation unit is a recorded selected-path edge,
not a new independent model sample. The report's aggregate transition matrix
covers complete declared paths, while checkpoint distributions cover only the
requested ordinals. A no-op, repeated test or assignment correction never creates
another generation root. Current evidence is applied to the same historical
programs; the trace does not reconstruct which label a reviewer believed earlier.

## Available cases and matched runs

Available-case counts include at most one selected-path artifact per run at the
exact checkpoint. The matched cohort is the intersection of observed run IDs at
every requested checkpoint. Classification and test passing do not determine
matched membership. Matching exclusions retain the missing checkpoints.

Both views show observed and requested counts, admitted coverage, validity
states, all-classified and valid-classified distributions, root-group declarations
and byte inventories. An unrecorded planned run remains in the available-case
requested denominator. Missing outputs do not become failed tests. Matching can
select difficult or long-running cases, so its result remains conditional on the
named subset; it does not remove survivorship bias or establish independence.

Numeric change checks use the participating view's runs. The configuration must
have known model, prompt, settings and selection rule, with a supplied common
protocol and equal known budgets. A fully observed matched subset can therefore
qualify even when an excluded run has an unknown budget; that unknown still
appears in the roster-level status. No hidden budget or condition is inferred.

Mechanism contrasts require unchanged membership and complete admitted mechanism
coverage at both compared checkpoints. If a label becomes unresolved, the
inventories still expose the changed count, but the output does not declare a
qualified concentration trend. At least two admitted observations are required
for trace concentration. Single-observation SCI/Gini-Simpson are
`not_applicable`; empty populations have zero support and undefined SCI.

Finite-pass contrasts additionally require all compared observations to have
definite finite validity and a common suite hash, oracle, environment fingerprint,
execution basis and known receipt visibility. Switching from feedback tests to
withheld evaluation changes that scope. Missing receipts, changed tests,
partial/timeout results and unknown visibility make the finite-pass comparison
unavailable. An otherwise compatible mechanism contrast can remain available.

Joint summaries derive finite-pass, support and concentration directions from
those exact operands. They can show correctness rising with support falling,
correctness rising with stable support, growing support, decreasing correctness,
stable outcomes, or insufficient comparable evidence. There is no universal
collapse threshold or preference for a particular direction.

Observed-set output gives retained, no-longer-observed, newly observed and
observed-again classes with the actual reference denominator. In changing or
incompatible cohorts these are labelled `inventory_only`. Reappearance is an
observed visitation fact, without an External Recovery Rate or capacity-recovery
claim. Structural Half-Life is not applicable to this revision clock.

## Designed examples and reproduction

The shared graph study contains 17 stipulated run histories, 45 revisions and
six reviewed project-owned programs. Two extra bad-increment implementations are
deliberately outside the automatic rule subset; their mechanism labels use the
explicit `fixture_only` policy. No new automatic graph rule is claimed by C04.

`tools/build_trace_example.py` executes only those fixed owned references and
increment defects, creating 74 receipts with 740 actual finite-case outcomes.
Evaluation receipts are withheld; separately executed feedback receipts are
agent-visible in the stipulated histories. A final repeated test adds evidence
to the existing revision. Histories, agent exposure, conditions and budgets
remain designed fixture claims, with zero model calls.

| Design | Passing / observed | All-classified support | All-classified SCI |
| --- | --- | --- | --- |
| `concentration.json` | 2/6, 4/6, 6/6 | 3, 2, 1 | 7/18, 5/9, 1 |
| `stable.json` | 2/6, 4/6, 6/6 | 3, 3, 3 | 7/18 at each checkpoint |
| `attrition.json`, available | 2/5, 2/2, 2/2; one additional planned run unrecorded | 3, 1, 1 | 11/25, 1, 1; membership changes |
| `attrition.json`, matched | 0/2, 2/2, 2/2 | 1, 1, 1 | 1 at each checkpoint |

The first example's valid-classified counts are FIFO=2, then FIFO=3/SETTLE=1,
then FIFO=6. Valid-classified SCI is 1, 5/8, 1, a nonmonotonic sequence despite
the increasing all-classified concentration. This cross-tabulation is retained
instead of inferred from marginal passing counts.

In the attrition example two early-success runs and one timeout leave the later
available population. Its apparent loss of SETTLE and RELAX is a change in which
runs are observed. The two fully observed runs remain FIFO while their finite
passing improves. Their cohort identities and the excluded runs stay visible.

```bash
python3 -m unittest discover -s tests -v
python3 -m structdet_code trace --study examples/trace/study.json --design examples/trace/concentration.json --format json
python3 -m structdet_code trace --study examples/trace/study.json --design examples/trace/stable.json --format markdown
python3 -m structdet_code trace --study examples/trace/study.json --design examples/trace/attrition.json --format markdown
```

JSON is canonical and Markdown renders it directly. Raw programs, prompts,
settings, protocol text and free-form logs are omitted from ordinary reports.
Exact study, design, task, source, assignment and receipt identities remain.
Malformed or stale data returns exit 2 with a bounded error. Valid records with
unavailable conclusions return exit 0. A design is limited to 1 MiB, and the
formatted canonical result to 4 MiB; size refusal does not silently truncate a
successful result. Existing per-study/parser limits still apply.

These fixtures verify software semantics, not empirical agent convergence or
classifier generalization. C05 covers integrated intervention/correction/replay
and the remaining demonstrations; C06 qualifies installations and release use.
