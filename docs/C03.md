# C03 graph task and condition comparison

Development version 0.1.0.dev3. All production commands remain passive. The
available source workflow is verified on Linux with CPython 3.12.14.

## Graph input and recognition

```bash
python3 -m structdet_code prepare --task unit-graph-distances --sources /absolute/path/to/python-sources --output /absolute/path/to/new-graph-study
python3 -m structdet_code inspect --study /absolute/path/to/new-graph-study/study.json --format markdown
```

The required entry point is `shortest_distances(node_count, edges, start)`.
Use 1..128 vertices numbered from zero and a list of 0..16384 directed pairs.
Every edge has unit cost; loops and repeated pairs are allowed. Booleans, weighted
triples and vertices outside the range fail the suite contract. Return a new
length-n plain list of minimum integer hop distances with `None` for unreachable
vertices. The start distance is zero; input lists and pairs stay unchanged.

| Hard class | Operative distinction | Boundary |
| --- | --- | --- |
| `DIST-FIFO` | FIFO first discovery or explicit breadth layers; each vertex enters the frontier once | Re-enqueueing after improved labels needs another descriptor |
| `DIST-SETTLE` | Select the globally smallest finite tentative label among unsettled vertices, finalize once, update outgoing neighbors | Unit-edge FIFO does not become settlement merely because its distances are nondecreasing |
| `DIST-RELAX` | Repeated passes over the full edge relation, improving labels until a round bound or fixed point | A relaxation helper inside another mechanism does not add a class |

Four rules in `graph_rules.py` cover FIFO, FIFO with a wrong increment, scanning
minimum settlement and repeated edge passes. Scope
`unit-graph-whole-module-alpha-ast/1` uses the C02 complete-module matching policy.
Formatting, comments, leading docstrings and consistent non-reserved identifier
renaming may vary. Helper changes, alternative containers or extra branches can
remain unrecognized even when a reviewer knows their mechanism. Recognition is
bounded to these rules; no generic equivalence solver or algorithm classifier is
claimed. A recognized label alone does not establish correctness.

The graph task uses the existing source-bound review template and `apply-review`
commands. Imports and opaque solvers remain unresolved; model proposals remain
unadmitted. Reachable hybrids and uncovered mechanisms retain reasons such as
`hybrid` or `schema_gap` when supplied review establishes those reasons. Mere
failure to match a rule is `insufficient_evidence`, not an inferred hybrid.

## Supplied graph test receipts

The literal suite file has this shape:

```json
{
  "schema_version": "structdet-code.graph-suite/0.1",
  "oracle_id": "unit-distance-properties/0.1",
  "cases": [
    {"id": "chain", "input": {"node_count": 3, "edges": [[0, 1], [1, 2]], "start": 0}}
  ]
}
```

It uses the existing study suite/receipt binding fields. The receipt states the
suite hash, source hash, revision, environment, counts, execution basis and
supplied conformance. Real descriptive material requires `external_report`.
Intake checks those records without invoking the oracle or candidate. A complete
passing receipt with passing conformance yields `passed_under_supplied_scope`;
it is a finite-suite observation, with no authenticated execution claim.

## Prepare a comparison

```bash
python3 -m structdet_code comparison-template --left left/study.json --right right/study.json --output comparison.json
python3 -m structdet_code compare --left left/study.json --right right/study.json --design comparison.json --format markdown
```

The output template must be new. Its two study hashes and selected revision IDs
are populated. Positions and collection metadata remain null until supplied from
the actual collection records. Editing the template cannot authenticate those
claims. If there are several configurations, choose one and retain slot entries
only for its selected revisions. The studies' own `selection` fields determine
which revision of each run is eligible; C03 does not select a later successful
revision for you.

| Design field | Meaning |
| --- | --- |
| `schema_version` | `structdet-code.comparison/0.1` |
| `comparison_id` | Bounded ASCII identifier |
| `varied_field` | Exactly one of `model`, `prompt`, `settings`, or null while unknown |
| `protocol_ref` | Supplied common collection protocol reference, or null |
| `prefix_size` | Common number of collection positions to retain, 1..128, or null |
| `selection_rule` | `fixed_prefix/0.1` |
| `left`, `right` | Study-bound side records described below |
| `side.study_sha256` | Exact manifest bytes, regenerated when the manifest changes |
| `side.configuration_id` | One existing configuration ID, or null |
| `side.planned_positions` | Supplied planned position count, 1..10000, or null |
| `side.budget_per_slot` | `{ "unit": "attempts", "limit": 1 }`, or null; also accepts `model_calls`, `generated_tokens`, `wall_seconds`; integer limit 1..1000000000 |
| `side.slots` | At most 256 records containing `position` and `revision_id` |

Each selected revision from the chosen configuration must appear exactly once.
Positions are unique positive integers within the planned count. A null position
is unknown and prevents prefix construction. A null revision at a known position
means an explicit missing output. Account for every position from 1 through the
prefix size. Include later selected revisions at their actual positions, so they
can be disclosed as excluded. An omitted slot is incomplete accounting, not an
automatically assumed missing output. Never renumber positions after failures or
replace gaps with later successes.

The per-slot budget is a supplied limit, not measured expenditure. The common
protocol should describe what a collection position means, how within-run
selection was fixed, and which budget applied. Model/prompt/settings and the
within-run `selection_rule` come from the study configurations. All must be known;
the declared varied field must differ and the other fields must match exactly
after canonical JSON encoding. Prompt strings retain exact whitespace. A single
`settings` change may encompass several settings, so no individual-setting effect
is inferred. Null values on both sides do not establish equivalence.

## Interpret results

`compatible_descriptive` means the supplied fields satisfy the stated comparison
requirements. `descriptive_only` returns inventories and specific missing or
incompatible prerequisites. Both are successful analysis outcomes with exit 0.
Malformed fields, duplicate positions/revisions, foreign revision IDs, stale
study bindings and unsafe files return the existing exit-2 bounded JSON error.

Without `--design`, `compare` returns the same honest incomplete-design view as
an unfilled template. Inventories are identified as either a chosen configuration
or all selected configurations when no configuration is chosen. No contrast is
computed from the latter aggregate. Sorting comparisons use these same commands
and checks, with sorting studies on both sides. Cross-task comparisons display
separate inventories and a task-mismatch reason; task labels are never pooled.

The canonical JSON contains each prefix's observations, declared root groups,
source identities, missing positions, later exclusions, admitted counts,
classification coverage, and validity states. Coverage uses both observed and
requested-slot denominators. `observed_pass_fraction` is finite passing divided
by observed outputs. `observed_pass_coverage_requested` is observed finite passing
divided by requested positions; it does not classify missing outputs as failures.

`classified_all` compares admitted mechanism distributions. `classified_valid`
additionally requires supplied passing finite validity. Every observed prefix
output must have a receipt, and both sides must share one exact suite hash,
oracle identity, environment fingerprint and execution basis, before the latter
contrast is available. Failed/partial/timeout receipts remain visible. A changed
suite or missing receipt blocks the valid comparison while leaving an otherwise
compatible all-classified comparison available. IDs may differ if scope content
matches. Unselected receipts and later excluded outputs do not change prefix scope.

Differences are right minus left, with exact signed fractions and both admitted
population sizes. An empty classified population has zero support and undefined
SCI; it produces an unavailable delta. Coverage differences, shared sources and
supplied root groups remain visible. These values establish no causal model
effect, independent sampling, population uncertainty, degradation or capacity
estimate. Markdown is rendered from that same JSON object. Reports fingerprint
conditions and the protocol without emitting raw prompt/settings/protocol text.

## Designed example

```bash
python3 -m structdet_code compare --left examples/graph/left/study.json --right examples/graph/right/study.json --design examples/graph/comparison.json --format markdown
```

The example is project-owned software-test material. Its configuration names,
collection positions and budget are stipulated. No real model was sampled. The
eight program snapshots have 80 actual finite-case executions from the fixed
developer utility. Seven snapshots pass all ten cases; the wrong-increment FIFO
passes four and fails six. Its mechanism remains `DIST-FIFO`.

| View | Left | Right, prefix positions 1..4 |
| --- | --- | --- |
| Observed / requested | 4 / 4 | 3 / 4; position 3 missing |
| Classified | FIFO 2, SETTLE 1, RELAX 1 | FIFO 3 |
| Finite-passing classified | FIFO 2, SETTLE 1, RELAX 1 | FIFO 2; failed position 2 retained in the all view |
| All-classified SCI | 3/8 | 1 |
| Valid-classified SCI | 3/8 | 1 |
| Later selected output | none | SETTLE at position 5, excluded |

Each contrast has SCI delta 5/8, support delta -2 and Gini-Simpson delta -5/8.
The denominators differ and remain explicit. One identical source appears in
both prefixes; all snapshots share a declared project-fixture root group. This
fixture demonstrates selection arithmetic and evidence handling, not a model
comparison or independent classifier evaluation.

Verification results and remaining C04-C06 work are in `verification/C03.md`.
Graph descriptor prose and Python programs are independently written. Algorithm
background: Sedgewick and Wayne's [directed graph](https://algs4.cs.princeton.edu/42digraph/)
and [shortest path](https://algs4.cs.princeton.edu/44sp/) chapters.
